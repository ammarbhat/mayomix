# Mayo-Mix API

The backend for **Mayo-Mix**, a music review and sharing app in the spirit of Letterboxd, built for albums and songs. Users rate and review albums, curate a profile of their own taste, and connect with friends to see what they're listening to.

Album, artist and song data comes from the [MusicBrainz](https://musicbrainz.org) API and cover art from the [Cover Art Archive](https://coverartarchive.org), so the app only stores what belongs to the user.

> This repo is the API only. The frontend lives in a separate project.

## Features

- **Accounts and auth**: registration, login, and JWT-protected routes. Passwords are hashed with Argon2.
- **Profiles**: name, bio, profile picture link and favorite genres, viewable by anyone.
- **Taste entries**: a hand-curated list of top songs, top artists, top genres, top albums and a current "rotation". These are set by the user, never inferred from listening data.
- **Album reviews**: a rating and written review per album, one review per user per album.
- **Connections**: mutual friend requests. A request can be sent, accepted, declined or removed.
- **Activity feed**: recent reviews from you and your accepted connections.
- **MusicBrainz proxy**: search for albums, artists and songs with pagination, and fetch album details with cover art. Album search is tuned toward the user's favorite genres.

## Getting started

### Prerequisites

- Python 3.14 or newer
- [uv](https://docs.astral.sh/uv/)

### Setup

```bash
git clone https://github.com/ammarbhat/mayomix.git
cd mayomix
uv sync
```

Create a `.env` file in the project root:

```
SECRET_KEY=replace-with-a-long-random-string
```

You can generate a suitable key with `python -c "import secrets; print(secrets.token_hex(32))"`.

### Run the server

```bash
uv run fastapi dev
```

The API is served at `http://127.0.0.1:8000`. Tables are created automatically on startup, and the SQLite database file is created on first run.

Interactive API docs are generated by FastAPI:

- Swagger UI: `http://127.0.0.1:8000/docs`
- ReDoc: `http://127.0.0.1:8000/redoc`

### Run the tests

```bash
uv run pytest
```

Tests run against an in-memory SQLite database that is created and dropped for every test, with authentication replaced by a seeded test user through FastAPI's dependency overrides.

## API overview

The docs page above is the authoritative reference. At a glance:

| Area | What it covers |
| --- | --- |
| Auth | Register a user, log in and receive a token |
| Users | View your own profile, view another user's profile, edit, delete (requires password confirmation) |
| Taste | Add, list, edit and remove entries for songs, artists, genres, albums and rotation |
| Reviews | Create, read, edit and delete reviews, list by user or by album |
| Connections | Send, accept, decline and remove requests, list connections and pending requests |
| Activity | Feed of recent reviews from you and your connections |
| Search and albums | MusicBrainz-backed search and album detail lookup |

## Design notes

- **Store IDs, not metadata.** Songs, albums and artists are saved as MusicBrainz IDs (MBIDs) and the details are fetched when needed. This avoids duplicating data the source already keeps accurate.
- **Constraints as a backstop.** Rules such as one review per user per album and unique ranks within a taste category are enforced in the database as well as in the endpoints, so a bug or race condition can't quietly corrupt data.
- **Ownership comes from the token.** Self-referencing actions read the current user from the JWT rather than trusting an ID sent by the client.
- **Async only where it pays off.** Endpoints that call MusicBrainz are `async`. Database-only endpoints are plain `def`, which FastAPI runs in a thread pool.
- **Taking care with MusicBrainz.** Requests send an identifying `User-Agent`, and the API's data is inconsistent by nature, so responses are handled defensively. For example, the best release for cover art is chosen by preferring official releases, an exact title match and the earliest date.
